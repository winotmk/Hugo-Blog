写博客这件事，表面上不过是打开编辑器、写一篇 Markdown，再把页面传到服务器。但我折腾了一圈之后，发现自己花在\*\*“怎么把文章发布出去”\*\*上的时间，可能比写文章还多。

从最初在 VS Code 里写文、借助插件管理 Front Matter，到把文章同步到云服务器、执行部署脚本，我的博客经历过好几次改造。最近，我又给自己开发了一款专门的写作工具 **Winotypo**，把文章编辑、属性管理和 Git 推送放进了同一个界面。

而在 Winotypo 后面，我还保留着两套不同的博客：一套使用 **Hugo**，发布到阿里云 OSS；另一套使用 **Hexo**，发布到 GitHub Pages。

我给这整套流程起了个名字：**双构建博客管线（Dual-Build Blog Pipeline）**。

它听上去有点像在为个人博客过度设计，但对我来说，折腾这套系统本身也是写技术博客的一部分。

## 一篇文章，为什么要构建两次？

现在我的两个博客入口分别是：

* **Hugo**：<https://md.winotmk.com/>
* **Hexo**：<https://winotmk.github.io/>

它们的主题、生成器和部署目标并不相同，但文章内容来自同一个地方。

我不希望维护两份 Markdown，也不想为了两个网站分别登录后台、复制粘贴内容。对我来说，理想状态应该是：**文章只写一次；至于最后生成几套网站，由发布系统自己处理。**

这里最关键的设计，并不是同时使用 Hugo 和 Hexo，而是把**内容源**和**网站实现**分开。将来哪怕我换掉其中一个生成器，原始文章也不需要跟着搬家。

## 整条管线长什么样？

现在的主要流程可以画成这样：

```text
                      Winotypo
               写作 / 预览 / Front Matter
                        │
                    Git Push
                        ▼
             GitHub：winotmk/Blog-Posts
                 唯一的 Markdown 内容源
                        │
              提交信息包含 [D] 时
                        ▼
                GitHub Actions
            sync-deploy.yml 同步文章
                   ┌────┴────┐
                   │         │
                   ▼         ▼
           Hugo-Blog       Hexo-Blog
          content/posts   source/_posts
                   │         │
            Hugo 构建      Hexo 构建
                   │         │
             Rclone 部署   Pages 部署
                   │         │
                   ▼         ▼
             阿里云 OSS    GitHub Pages
                   │         │
                   ▼         ▼
          md.winotmk.com  winotmk.github.io

   独立图床 pictures.winotmk.com 为文章提供图片资源
```

我把它大致拆成了四层：**写作工具、内容仓库、分发构建、静态托管**。每层只负责自己的事。

## 第一层：用 Winotypo 写文章

![1.00](http://pictures.winotmk.com/winotypo/f320157dd871bbe45e0275799ba890b74f874a0e1753e0ecba266456604dd891.png)

以前，我主要使用 VS Code 写 Markdown，配合 Front Matter CMS 管理文章的日期、分类和标签。这套组合已经足够好用，但日常写博客时，我还是希望操作更集中一点。

于是有了 **Winotypo**。

这个工具可能有点类似<https://bestofjs.org/projects/zettlr>

**主要是内容编辑与最终呈现相互分离。** 但严格来说，Zettlr 更接近一个「本地优先的 Markdown 写作工作台」，而我的 Winotypo 已经向「Git 驱动的无头 CMS 客户端」发展了

在同一个界面里，我可以浏览文章列表、编辑和预览 Markdown、设置标题图、分类、标签与发布日期，也能查看文章的同步状态和已发布链接。写完以后直接推送到 Git 仓库，不必再来回切换编辑器、Git 客户端和网页。

不过，Winotypo 并不是整套系统的“内容数据库”。**真正的文章仍然是一份份普通的 Markdown 文件。**

这一点我很看重：如果某天不再使用 Winotypo，我仍然能用 VS Code、Obsidian 或任何文本编辑器打开它们。工具可以换，内容不应该被锁在工具里。

## 第二层：Blog-Posts 是唯一的文章源

所有文章统一保存在：

<https://github.com/winotmk/Blog-Posts>

主要内容位于仓库的 `posts/` 目录。我在这里维护文章，而不是直接去修改 Hugo 的 `content/posts/` 或 Hexo 的 `source/_posts/`。

这个仓库实际上承担了一个轻量级内容管理后端的角色：Git 负责记录历史版本，GitHub 负责保存和分发；至于如何把 Markdown 变成网页，则由下游仓库决定。

不过，我也不希望每次随手提交都立刻发布。所以目前的同步工作流带有一个小开关：**提交信息中包含 `[D]`，才执行文章分发**。

对应的触发条件大致是：

```yaml
on:
  push:
    branches:
      - main

jobs:
  sync-posts:
    if: contains(github.event.head_commit.message, '[D]')
```

这样，“保存到 GitHub”和“正式启动发布”就可以分开控制。

## 第三层：一份 Markdown，自动分发给 Hugo 和 Hexo

触发后，`Blog-Posts` 的 GitHub Actions 会拉取两个目标仓库，并分别把文章同步到：

* `Hugo-Blog/content/posts/`
* `Hexo-Blog/source/_posts/`

同步使用的是 `rsync`，其中 `--checksum` 用来按内容比较变化，`--delete` 用来处理已经从文章源中删除的 Markdown。同步范围限定为 `.md` 文件。

这意味着新增、修改、删除文章，都可以从 `Blog-Posts` 这个入口向下游传递，而不是每次人工维护两份目录。

如果某个目标仓库确实发生变化，工作流就会自动提交并推送它。新的 Push 又会触发那个博客仓库自己的部署 Action。

因此，这里实际上有**两级自动化**：

1. `Blog-Posts` 负责把内容分发到不同的构建仓库。
2. 各博客仓库负责把内容变成静态网站，再部署到自己的托管平台。

这两级之间靠 Git 提交衔接，不需要我长期维护一台负责发布的云服务器。

## 第四层：两条互不依赖的构建与发布路线

### Hugo：生成静态文件，增量发布到阿里云 OSS

Hugo 仓库位于：

<https://github.com/winotmk/Hugo-Blog>

收到新的文章提交之后，Action 安装指定版本的 Hugo，拉取主题子模块，然后执行构建。当前的构建命令是：

```bash
hugo --minify -D --destination "$RUNNER_TEMP/hugo-public"
```

生成后的 HTML、CSS、索引页等文件会放到 Runner 的临时目录，再发布到 OSS Bucket `winhugoblog`，供 `md.winotmk.com` 访问。

我最近还专门优化了这部分。之前使用 `ossutil cp -rf`，每次部署都会重复上传大量没有变化的文件。有一次日志里，**Hugo 构建只用了约 0.57 秒，而 OSS 上传用了约 81 秒**。瓶颈根本不在生成页面，而在发布方式。

现在这一侧改用了 **Rclone 配合部署脚本**：先比较本地构建文件和 OSS 对象的大小、MD5 等信息，再结合部署清单决定哪些文件需要上传、哪些旧页面需要清理。这样既能减少重复传输，也不会盲目删除整个 Bucket 中不属于本次部署清单的对象。

对于总量不算大的静态博客，这种优化已经很实用。

### Hexo：构建另一套网站，发布到 GitHub Pages

Hexo 仓库位于：

<https://github.com/winotmk/Hexo-Blog>

它收到新的文章提交后，使用 Node.js 环境安装依赖，运行 `hexo generate` 生成静态站点，再通过 GitHub Actions 将构建结果推送到 `winotmk/winotmk.github.io` 仓库的 `hexo-new-deploy` 分支，由 GitHub Pages 提供访问。

于是，同一篇 Markdown 就有了第二种展示方式，以及一套不同的托管环境。

这里所谓的“双构建”，不是构建同一个 Hugo 网站两遍，而是让**两种独立的静态站点生成器分别消费同一份内容**。

## 图片为什么单独放？

我的文章经常会包含截图、示意图和其他图片资源。现在我把图片统一放在独立图床 `pictures.winotmk.com`，Markdown 里只保留图片链接。

这样一来，文章仓库主要保存文本，两个网站构建时也不需要反复复制同一批大图。图片资源与网页发布彼此独立，迁移或重建网站时会轻松不少。

当然，这也意味着图床变成了两套网站共同依赖的基础设施。以后如果要做完整备份，除了 Markdown 和网站代码，还必须记得备份图床。

## 这套架构让我得到什么？

回头看，这套流程最有价值的并不是节省了多少秒的点击操作，而是几个边界终于变得清晰：

**文章只维护一份。** `Blog-Posts` 是唯一的内容源，不再担心 Hugo 和 Hexo 的文章版本不一致。

**写作不依赖构建器。** Winotypo 只需产出符合约定的 Markdown 和 Front Matter，不必知道 Hugo、Hexo 具体如何渲染。

**两个网站可以独立演进。** 我可以在 Hugo 上调整主题或部署方式，而不需要修改 Hexo 的配置，更不需要修改文章源。

**Git 提供了天然的版本记录。** 什么时候修改了文章、修改了什么、能不能回退，都有清晰的历史。

**发布流程不再绑在自己的云服务器上。** GitHub Actions 完成分发和构建，静态文件交给 OSS 与 GitHub Pages 托管。

用软件架构里的说法，这有点像一个以 Git 为存储层的轻量级 Headless CMS：前面是专用写作客户端，中间是内容仓库，后面接两套彼此独立的渲染和发布系统。

当然，它并不是传统意义上提供管理后台和 API 的完整 CMS；我只是借鉴了**内容与表现分离**的思路。

## 还有哪些地方没做完？

目前这套系统已经可以日常使用，但我并不认为它没有问题。

首先，**“已同步”不等于“已发布”**。Winotypo 把文章推送到 GitHub，只能说明源仓库更新了。后面还有分发、Hugo 构建、OSS 上传、Hexo 构建和 Pages 发布等环节。任何一步失败，都可能出现 Git 里有新文章、网站上却看不到的情况。

我希望以后能在 Winotypo 里直接看到两条发布链的状态：文章已提交、已分发、Hugo 部署成功、Hexo 部署成功。如果失败，也能看到对应的 Actions 运行记录，而不是再到几个仓库里逐一排查。

其次，**两种生成器对文章元数据的理解不一定完全相同**。日期和时区、草稿、未来文章、摘要、永久链接等，都需要明确约定。之前我就遇到过 Hugo 因为时区解释问题，把一篇刚写好的文章当成“未来文章”而没有生成。现在 Hugo 已经设置了 `Asia/Shanghai`，但双端发布规则仍然值得继续统一。

最后，当前文章分发工作流还是依次推送 Hugo 和 Hexo。未来如果想进一步提高容错性，可以将两条下游同步拆成独立任务：一边出问题，不影响另一边继续发布。

这些都属于下一阶段的完善，而不是为了技术而技术地继续增加复杂度。

## 写在最后

从 VS Code、Front Matter CMS，到今天的 Winotypo；从云服务器上的脚本，到 GitHub Actions 自动分发；从每次全量上传，到只处理真正变化的静态文件，我的博客发布流程已经不知不觉变成了一套小型系统。

有人可能觉得，写个博客而已，为什么要搞得这么复杂？

对我来说，答案其实很简单：**一方面，我希望日常写文章足够省心；另一方面，我也确实喜欢研究这些工具究竟该怎样组合起来。**

现在，我只需要在 Winotypo 里写完文章，决定发布，然后把剩下的事交给 Git 和自动化管线。

文章只有一份，网站可以有两套，甚至未来可以有更多套。最重要的是，**写作属于写作，构建属于构建，发布属于发布。**

这就是我的“双构建博客管线”。
